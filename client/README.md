## 实测纠正了计划的事实（逐条编号；条数不写进标题，免得又漂一处）

1. **事件数是 56 不是 44**：`src/server/protocol.ts` 的 `SessionEventType` 实测 56 个成员（两种独立提取法互校一致）。
2. **建连时序**：`replay_window → delegation_snapshot → job_snapshot →（zen_phase 镜像）→ 回放 → gap → approval_snapshot → live`，与 §4.3 #1 描述一致；`approval_snapshot` 正是 live 交接标记（`session-routes.ts:1825` 紧接 `catchingUp = false`），已作为客户端判定依据并在真实连接上验证。
3. **`GET /events` 不是会话事件流**：实测为 5 秒 `hello`/`health` 心跳通道，无 `seq` 无语义；会话列表失效改用 `sessionCount:runningCount` 签名变化。计划把它列为「失效刷新」源，实现按真实语义接。
4. **§2.3 那行 P0「OpenHands 的 last-event-id 断线续传」在天枢 sidecar 上根本没有这条通路**（2026-10-10 现数）：`grep -rin "last-event-id|lastEventId" src/` **0 命中**，而 `src/server/sse-stream.ts:42-48` 写帧只有 `event:` 与 `data:` 两行、**不发 `id:` 字段**——两头都不支持 SSE 标准续传。所以唯一可行的机制就是内核自己的 `?since=<游标>`，客户端也正是这么接的（`session-stream.ts` 的注释另外还有一条独立理由：EventSource 不能带 `Authorization` 头）。计划的 P0 陈述照抄会写出一个假实现，这里按实测语义纠正；顺带一条边界：**将来内核若真发 `id:` 并支持 `Last-Event-ID`，客户端不该改用它**——那会把"游标由客户端掌握"变成"由服务端掌握"，而我们的去重与世代判定都建立在前者上。
5. **§2.3 那行 P2「OpenCode 的 `/tui` 反向控制端点（server 驱动客户端 UI）」在天枢没有对应物**：`src/server/` 里 `./tui/...` 全是**内核内部模块 import**（剪贴板、handoff、cockpit 状态等），没有任何 HTTP 路由把 UI 控制权从 server 推给客户端。计划把它列为「P2（可选）」，实测结论是**没有可接的端点**，不是"我们没接"。
6. **§4.4 桌面那一格写的「preload 只暴露窗口控制/文件对话框」比实现**宽松**，而实现走的是更严的姿态**：桌面壳**根本没有 preload**（`apps/desktop/src/main.mjs:204` 那句 "No preload: the renderer is a pure web app over loopback HTTP"，且 `verify-desktop.mjs` 第 276 行的姿态判定要求 `!/preload\s*:/` 与 `sandbox:true`、`contextIsolation:true`、`nodeIntegration:false`、`webviewTag:false` 同时成立）。为什么不缺：窗口控制交给 OS 画的标题栏与主进程自己的菜单/快捷键，渲染进程不需要 Node；文件选择走浏览器自己的 picker 与 sidecar 的文件端点，**没有需要 IPC 的能力**。代价与联动写清：**如果**将来采纳那条搁置的「40px 自绘标题栏」（§5.2 之后的几何决定之一），`frame:false` 之后最小化/最大化必须从渲染进程走 IPC，那时**才会**出现一条窄 preload——这正是我把那格标成"特权面取舍而不是配色决定"的原因，也是这条判定的边界。
7. **§4.3 #3 写「markdown 只重解析尾部 2 个不稳定块」，实现里的不稳定区是 1 个**：`ui-primitives/src/markdown.ts` 只重解析 `open` 的那一块，其余全走缓存。"2" 在这套折叠模型里没有对应物——一个回合的 delta 全折进**同一个**开放块（`session-model.ts:340`），块一封口就不可变，多算一个只会白解析。同时核掉一个真会咬人的前提：**缓存按块 id 取、忽略传入 source**，所以 id 绝不可复用——`SessionModel` 用单调 `this.nextId++`，且**历史向上分页重导出时间线时也不重置**（`prependEvents` 走 `emptyState()` 重新折一遍，新旧块各取新 id），因此不会拿回上一内容的 HTML。另附一条方法上的收获：**这条 O(n²) 修复此前只由一次性测量脚本撑着**（树里没有任何东西钉它，删掉缓存查找全都绿）——现在由 `markdownParseCount` + 两条测试钉住，见「途中修掉的真实缺陷」最上面那条。

## provider 配置：走过的弯路（M0 #4 曾长期阻塞于此）

凭据处置经过（都留了证据，避免下次重新踩）：

1. key 最初被贴在 `config.example.json` 的 `provider.providers.deepseek.apiKeyEnv` 里——**两个错**：`apiKeyEnv` 是环境变量**名**字段（运行时去查 `process.env['sk-…']`），且示例文件不是活动配置。结果 `GET /health` 一直 `configured: false`。
2. 该文件是**被 git 跟踪**的，而本仓同步到公开投影 → 明文有外泄风险（当时尚未 staged、未进历史）。
3. 修法：`scripts/relocate-credential.mjs` 把明文搬到 `client/.sidecar-data/config.json`（gitignored、0600），由 `launch-sidecar.mjs` 经 `RIVET_CONFIG_PATH` 注入（`src/config/paths.ts:38` 该变量优先）。运行时按自身设计把明文进一步收进 `.sidecar-data/secrets.json`，配置里只留 `keyRef` 指针。`config.example.json` 已还原到 HEAD，工作树 tracked 改动为零。
4. 之后 `configured: true`，但 run 仍失败：会话默认解析到 **kimi 的 `k3`**，在 deepseek 下查不到该模型，内核崩在 `Cannot read properties of undefined (reading 'id')`。显式 `POST /sessions {model:'deepseek-flash'}` 能被接受，同样崩溃；`GET /sessions/:id/models` 返回空数组——即该 provider 在此隔离配置下**没有模型目录**，`POST /config/providers {models:[{id}]}` 返回 ok 但目录仍空（模型挂在 `keys[].models` 上，未传 apiKey 就无处落）。
5. **真正根因（已解）**：模型表必须挂在 **key** 上而不是 provider 上。密钥迁移把 provider 变成「已迁移」态，`serve.ts:232` 的 `findModelOwner` 走 `provider → keys → models`，单池回退不再适用；`keys[].models` 为空 → `spec.model` undefined → 崩在 `serve-agent.ts:648`。正解是官方端点 `POST /config/providers/deepseek/keys/default/models`（不需凭据），之后 `PUT /config/default-model {defaultModel:'deepseek:deepseek-flash'}` 才通过校验。此前 4 次失败都在出门前，**未产生上游费用**；成功取证共 2 次真跑（一次短答、一次带工具调用的多轮 run）。

## 协议/运行时事实（写进设计依据）

- **审批回答的 `decision` 缺省即「放行」**：`approval-routes.ts:16-21` 是 `const decision = data.decision ?? 'approve'`，且 `remember` 走严格比较 `data.remember === true`。也就是说一个漏写 `decision` 的**拒绝**载荷在服务端会被读成批准——不报错、不 400，就静默做了用户刚拒绝的事。这类失败只在「离开面板的那串字节」里可见，界面上永远看不出来，所以三态载荷现在由 5 条单测钉住（`packages/ui-approval/src/answer.ts` + `test/answer.test.ts`：一次=纯 approve 且**不带 remember 字段**、只有「始终允许」带 `remember:true`、拒绝必须显式给 `decision`、三者两两不同、渲染顺序 primary→always→deny 且中英标签都能解析）。为了能让 `node:test` 进来，映射从 JSX 里抽成了无 JSX 模块（沿用本包 `before-view.ts`/`stall-watch.ts` 的既有做法）；`ui-approval` 其余部分不变，构建产物里三个标签与两个按钮类名都在。**没被这层测试覆盖的**是服务端受理之后发生什么（`remember` 是否真的改了会话档位、拒绝后工具是否确实没执行）——那要再打一发，仍是任务 #27。
- **内核已经给了「读剪贴板图片」这条路，客户端没接**：`src/server/clipboard-routes.ts:34` 的 `GET /clipboard/image`（Bearer 保护）返回 200 `{image: {dataUrl, mime, name} | null}`，剪贴板没图或取图工具缺失就是 `image: null`（内核注释明说这是为了 #302「前端无任何反应」那类失败可见化），取图链抛错才给 500 `{error}`。**这是服务端读剪贴板**，所以浏览器版不需要 `navigator.clipboard` 权限、桌面版**也不需要 Electron preload**——计划 §4.4 用 preload 换的那个「文件对话框」能力，在这里其实早就有一条协议内通路。当前 `grep` 过：client-core 与 `apps/web` 都没引用它。接不接由用户定（属计划外的新增能力，不擅自扩范围）。

- **delta 在落盘与回放时被压缩**：`replay-compaction.ts`（`session-routes.ts:1784` 应用）会把已闭合的 delta 串压成单条事件。所以「流式增量」只能在 live 通道观测——磁盘上同一段是 1 条。客户端按 seq 消费，不受影响；但**任何用回放/磁盘事件断言增量性的测试都是假测试**（我的第一版 accept-stream 就这样误判过，已改为按 live 通道的 delta seq 判定）。
- **`GET /sessions/search` 不覆盖 sidecar 会话库**：`session-search.ts:114` 按 `sessionsDir(session.cwd)` 解析项目本地 `<cwd>/.rivet/sessions/<id>.jsonl`，而 sidecar 写在 `RIVET_DESKTOP_DIR/sessions/`。实测任何查询都 `scannedFiles:1`、0 命中。属内核侧限制，已记为上游问题；搜索空态在 UI 上如实说明，不伪装成「无匹配」。
- **写 `apiKey` 会先被探针卡住**：`config-routes-keys.ts:150` 对 provider baseUrl 打连通性探针，不过就 400 不落盘（实测 `network-error`）。设计上是好设计——不存一个用不了的 key——但设置界面必须把拒绝**显式报错**，不能显示「已保存」。`apiKeyEnv` 分支不探针；且 `keyStatus` 报的是**生效**状态：指向一个进程里并不存在的环境变量会得到 `none` 而非 `env`，界面据此显示「未设置」。
- **`compactionState` 不只是「压缩中」**：实测取值含 `ready`/`healthy` 这类正常态，我最初「非 ready 就标压缩中」会长期挂一个假警报。现改为 `CALM_COMPACTION_STATES`（ready/healthy/idle/none）之外才显示。
- **`GET /cockpit` 只对在跑的 agent 有效**：归档或从未 run 过的会话返回 404 `Session agent not built yet`。Cockpit 条因此必须在 run 期间取，且 404 要当作「暂无 live 读数」静默处理，不是报错。
- **工具的真 diff 在 `uiContent`，不在 `result`**：`tool_result` 的 `result` 是给模型看的散文回执（「已写入 13 字节…」），unified diff 只在 `uiContent` 里，线上截到 **2000 字符**（`session-manager.ts:6243`），并由服务端自己的 `outputTruncated` 标志声明。客户端必须两个都收：只读 `result` 的界面永远看不见改动内容。`tool_use.input` 不被压缩，所以「将要写入」的意图始终是完整的。
- **`git/diff` 与 `git/file-base` 的越权行为是 500，不是 403**：`/file-content` 有 `validatePath` 显式拒绝（`session-routes.ts:1585`），这两条 git 路由没有 try/catch，路径逃逸时从 `git.ts:428` 抛出未处理异常 → 客户端收到 `Internal server error`。界面因此把非 200 归为「读不到基线」并显式报错，**不能**当作「这个文件本来就没内容」渲染成空面板。
- **调度器状态与写健康要一起看**：`GET /schedule/status` 的 `persistence.ok` 是设计给 30s 轮询用的——「上次保存没落盘」不能只在保存那一刻提示一次。看板因此常驻显示落盘状态。

- **工作台三条实测契约**：① porcelain 的空列是**一个空格**不是空串——`" M"` 是未暂存、`"M "` 是已暂存，用 `!== ''` 判断会把所有文件当已暂存（浏览器里真错过：干净树上一切都显示「已暂存 1」）；② `GET /git/workbench/branches` 把 `refs/heads` 与 `refs/remotes` 混成一个平铺列表、没有任何标记字段，分支选择器必须自己按「首段是否为已配置远端」过滤，否则会把 `origin/main` 当成可切分支；③ `POST /sessions/:id/git/commit` 提交的是**索引**（`commitIndex`），不是磁盘上的一切——未暂存的改动会得到 `nothingToCommit:true`，界面不能显示「已提交」。
- **写路由的 scope 在 body 里**：`/git/workbench/*` 的写请求把 `{cwd}` 或 `{sessionId}` 放 body（服务端 `{...params, ...body}` 合并后再解析目录），漏掉它得到的是 **400 `context_missing`**，不是 404——我最初给客户端加写方法时就漏了，是验收脚本抓出来的。
- **一个会话的 cwd 永远带着运行时自己写的 `.rivet/skills/**`**：它们是未跟踪文件，因此算「脏」，切分支/推送会直接被内核拒。要么按开发者惯例在 `.git/info/exclude` 里排除，要么界面上如实说明是谁弄脏的——不能假装可以绕过。

## 上游缺陷（客户端只能缓解，不改内核）

- **仓库自己的指导文档把 node 版本说成"钉死"，而真值是范围**（2026-10-12 早，核 `.github/workflows/ci.yml` 的屋规宣称时撞出来的）。三条互斥的说法里只有一条能真：`package.json` 的 `engines` 实测是 **`{"node": ">=24"}`**（配 `.npmrc` 的 `engine-strict=true`，所以低于 24 在 `npm ci` 阶段就被拒——这层强制是真的，但它是**下限**不是钉版）；而 `AGENTS.md:8` 写着"Node.js 24（engines 钉 24.18.0）"、`CLAUDE.md` 同样，`ci.yml:19` 的注释写着"engines 钉 24.1.0"。**两个假说法还互相矛盾**（24.18.0 vs 24.1.0），这本身就是它们都不可信的证据。为什么值得记：一个照"钉 24.18.0"去装 exact 版本的 agent/新机器，会以为自己符合约束而实际什么都没被保证；而 `ci.yml` 的注释是"低于 24 会在 npm ci 直接被拒"的正确后果、错的措辞。**本条已于 2026-10-15 改掉**（授权来自你早前那句「#101 顺手改」——我此前一直把它记成"仍待你"，那是台账过期）：`AGENTS.md:8`、`.rivet.md:3`、`CLAUDE.md:3`、`.github/workflows/ci.yml:19`、`analysis-reports/项目文档与对比报告.md:20` 五处统一到真值（根 `engines.node` = `">=24"`，`.npmrc` 有 `engine-strict=true` ⇒ 低于 24 在 `npm ci` 就被拒；**是下限不是钉版本**）。**并且这条现在有门了**：`check:docs` 新增一条判定，把 `package.json` 的真值与那五份"教约束"的文件里的 engines 版本号逐个比（五个文件各自抽到 `">=24"` ⇒ 没有一个在名册里却抽不到东西）；反例是把 `AGENTS.md` 退回"钉 24.18.0" ⇒ **exit 1 且点名文件与两个值**，按 md5 逐字节还原后复绿。台账里那些引用旧错值的句子是历史记录，故意不在门的面内——否则等于要求台账不许引用被纠正过的措辞。**另有一处我没动**：`.github/ISSUE_TEMPLATE/bug_report.yml:41` 的示例占位符写着 `Node 24.1.0`，那是给用户填的样例文本、不是对约束的宣称，改它等于替用户决定模板长相，所以只登记不动。


- **无 key 时 `POST /prompt` 的症状在 2026-10-11 现测下已经不是"静默悬挂"了**（本条按当前读数改写；旧记录写的"200 running 后事件 0 条、永远停 running"是 2026-10-09 的观察，内核侧应当改过）。今天 `node scripts/ci-smoke.mjs` 同一套脚本量到的是：`POST /prompt` 回 **200 `{status:'running'}`**，随后事件日志有 **4 条 `user,status,goal_state,error`**，会话记录最终 **`status=failed`**——也就是它**会自我报告**。冒烟脚本两种形状都写着：拿到 `error`/`done` 就打 `✓ an accepted keyless prompt reports itself`，一条都没拿到才打 `i upstream finding — silent run without a key`（所以"静默"这条路径仍在被监视，只是今天没触发）。**为什么客户端的看门狗还留着**：`status` 字段本身不是"受理证明"（200 只代表被接收），能测的事实只有 **seq 有没有推进**；两种症状下 `stall-watch` 都判得对，而它防的正是"没有任何症状的失效"——这条缺陷当年就是靠"看起来一切正常"活下来的。今天内核日志里仍会打 `[loop-stall] activities=none`（它知道不对劲），但已经有一条 `error` 事件把这件事抬到了协议层；`ci-smoke` 两种形状都覆盖（自我报告→打勾，全静默→打 finding），并且**只在 `/health` 报 `configured:false` 时才走这一步**，所以它零花费、可无人值守。
- **客户端侧的缓解是「发送静默看门狗」**（`client-core/stall-watch.ts`，4 条单测）：界面不能信 `status`，只能信「seq 有没有推进」。20 秒无动静就把状态条换成 `app.sendStalled`，并显式给出中止与去设置两条出路；任何 seq 前进（包括自己那条 user 回显）即解除，`busy`/`conflict` 走队列不武装，以免把正常的排队报成故障。
- **端到端那一面还差人看一眼**：`node scripts/stall-demo.mjs` 会起一套**空配置**（显式写 `config.json` 并用 `RIVET_CONFIG_PATH` 指过去）的 sidecar + 同源伺服，先验 `configured===false` 才肯交界面，然后**什么都不发**，把 URL 打给你。你在浏览器里新建会话、随便发一条，~20 秒后横幅就该出现。这一步我没自己跑：权限层把「起 sidecar 并发消息」当成可能产生付费调用的动作拦下（它无法看到那份配置是空的），我不绕道。脚本里也刻意没有任何 `POST /prompt`——发不发由人决定。
- **`GET /sessions/search` 在这台内核上永远 0 命中——路径两头不一致**（2026-10-11 实测，本条替换掉此前那句写反了的记录）。读取侧 `session-search.ts:114` 打开 `sessionsDir(cwd)/<id>.jsonl`，而 `sessionsDir()` 是 `rivetHome()/sessions/<项目 slug>`（`src/config/paths.ts:33-35, 98-101`，**不是**项目本地）；而 sidecar 这侧的事件流写在**另一个根**：`desktopSessionsDir()` = `desktopDir()/sessions/<id>/events.jsonl`（`src/config/paths.ts:110-112`；`phantom-resume-migration.ts:13` 举的实例就是 `~/.rivet/desktop/sessions/<id>/events.jsonl`）。内核自己的注释把两种布局讲得很清楚（`src/agent/resource-sensor.ts:88-97`：「CLI layout：`<id>.jsonl` + 可选 `<id>/events.jsonl`」对「Desktop layout：目录里有 events.jsonl」）——**搜索按 CLI 那种扁平文件读，桌面端写的是目录式，两棵树永不相交**；桌面布局下的其他读取点也都是目录式（`frontend-session-provider.ts:20,111` 的 `<id>/ui-history.jsonl`、`session-routes.ts:1506` 的 `<id>/cache-log.jsonl`）。**实测**：隔离 sidecar 里建会话、发一条无 key prompt，`GET /sessions/:id/events` 明确读回 `{"text":"…菠萝包与黄油needle7788…"}`，而 `GET /sessions/search` 对该全文、对「黄油」、对「菠萝」三次都回 `{"results":[],"meta":{"scannedFiles":1}}`——`scannedFiles` 数的是**尝试读的条数**（那个文件根本不存在，`read` 抛错被 `catch` 咽掉），所以它不是"读到了"的证据。客户端不改内核（非目标），只做两件事：① 空态把这条不一致讲清楚（不再说"没跑过的会话才搜不到"，那种说法会把一个坏掉的功能说成正常边界）；② `check:docs` 有一条判定同时读两头（目录式写入 + 扁平 `<id>.jsonl` 读取），**内核哪天对齐了这条会红**，逼我们重测搜索并改掉文案。同轮还纠正了自己上一轮的一句过度声称：文案里那句「扫过 N 份」当时依据的就是 `scannedFiles`，而它是尝试数——已改成「查了 N 个会话的转录位」。**顺带一条自家的隔离洞也修了**：`launch-sidecar.mjs` 以前只设 `RIVET_DESKTOP_DIR`/`RIVET_CONFIG_PATH`，**没设 `RIVET_HOME`**，所以被判定脚本发出去的那条无 key prompt 会把会话目录写进**操作者真正的 `~/.rivet/sessions/<slug>/`**（实测：不设 RIVET_HOME 时临时 home 下什么都没有，设了才出现 `sessions/ws-<hash>/<id>/`）。现在没做成默认，而是加了显式开关 `--isolate-home`（带上才把 `RIVET_HOME` 关进 `<desktopDir>/rivet-home`），三个会发 prompt 的自检脚本（`ci-smoke` 冒烟、`check:liverender`、`stall-demo`）都带上了；**不做默认**的理由：桌面壳本来就跑在操作者自己的 home 上（CLI 转录与缓存日志同在一处），挪它的数据根属于产品决定而不是测试顺手——所以现在 `verify-desktop` 直接把选择打在日志里（`rivet home: 默认（操作者的 ~/.rivet） — 加 --isolate-home 才关进临时目录`，17 项 exit 0），要不要连桌面端一起关起来由你定。
- **本地/无密钥端点在运行侧被拒，而 `/health` 说"已配置"**（2026-10-13 凌晨现场实测）。内核把「自定义 provider + `baseUrl` 指向 127.0.0.1 + 没有任何密钥材料」与 keyless 预设（`ollama`：`keyless: true`、`baseUrl: http://127.0.0.1:11434/v1`，`src/config/provider-presets.ts:1055-1062`）都算作**一等的 keyless 本地端点**——`src/config/provider-presets.ts:1157-1166` 的注释写明那是 keyless 判定的单一事实源，消费方是 `resolveApiKey` / `config/providers` / 欢迎页。`/health` 的 `configured` 走的正是这一套：现场脚本加一个 loopback provider 之后，`configured` 当场从 `false` 翻成 `true`。**可运行侧不看这个谓词**：`src/server/serve.ts:571` 的 `isModelSpecUsable` 只认 `spec.apiKey !== '' || spec.auth`，`src/server/serve-agent.ts:882` 在它不成立时直接拒绝发出请求。**实测两次都是同一句话**：① 自定义 loopback 条目 → `error` 事件「No usable API key for provider "loopback-spike" — the request was not sent」；② 内置 `ollama` 预设、`baseUrl` 指到我本地起的替身端点 → 同样的拒绝，而那台替身服务器**一发请求都没收到**（计数 0）——所以"本地模型跑不起来"不是网络或解析问题，是这道闸。`/config/providers/custom` 还拒绝用预设名注册（400 明写要用别的名字或走 `rivet config setup`），这条边界是清楚的。**对客户端的实际影响是一处会误导的安静**：`apps/web/src/App.tsx:619` 那句"没有可用密钥"的提示只在 `configured === false` 时出现，而 keyless 本地端点的 `configured` 是 `true`，界面因此不提示；好在此刻内核**不是静默的**——`error` 事件带着可读原文进时间线，用户看得见失败与原因（**这句当天就从推断变成了读数**：像素门 `check-live-geometry.mjs` 新发一条无 key prompt 拿真 `error` 事件，六条判定量到"错误块落成 1 块、正文与服务端 `data.error` 逐字相等、标题走 locale、用户那句也在、长错误串不破版、归档位勾了才列出"，见本节最上条）。**我没改内核，也没在客户端加"猜一层"的分支**：要在界面上对这句做二次判断，等于把内核的一处不一致复制成第二处事实源。**这条还有一层实际意义**：我原想用"本机替身上游"把台账里"要一次真 run 才量得到"那几格（真审批请求、真 diff 载荷、⚡ 的线上读数、断网续读、真 `lost` 时机）变成零花费实测——协议路径真跑、零美元、不碰任何真域名。spike 到这一步卡住了：过运行侧那道闸必须给 provider 存一个**内联密钥值**，那是往凭据面上写字，按规矩交回你拍板（已登记在交接第 1 条下面）。

## 已知边界（不粉饰）

- **同一句判死结论在 2026-10-14 对当前内核复测过，并且多排除掉一条我以为可能救它的旁路**（内核此刻正被包名迁移改着，所以这次是重读源码而不是沿用 10-11 的读数）。仍成立的两件：读取侧仍把语料拼成 `sessionsDir(cwd)/<id>.jsonl`（CLI 扁平式，见 `src/server/session-search.ts` 与 `src/config/paths.ts`），桌面侧仍写 `desktopSessionsDir()` 下的**每会话一个目录**（`<id>/events.jsonl`）——现场残留的 `.live-geometry/store/sessions/<id>/index.json` 就是目录式那一眼的实物。**新排除的一条**：`sessionsDir()` 其实有 `RIVET_SESSION_DIR` 覆盖、`desktopSessionsDir()` 也有 `RIVET_DESKTOP_SESSION_DIR`，所以"两棵树"单独看像是一个配置就能缝合的问题——**缝不上**：读取侧拼的文件名形状是 `<id>.jsonl`，把根指到桌面树之后它要找的是 `<桌面根>/<id>.jsonl`，而桌面上根本没有这个形状的文件。所以这条欠账的机制描述要写成**根与布局两处都不一致**，而不是只写根；写"确认没有免费路径"的那句必须带上这两条覆盖是试过的（我此前只说了两棵树，那是半个答案，容易让下一个人白试一遍 `RIVET_SESSION_DIR`）。第二件 `partial` 同样复测：读当前类型镜像的事件名清单，带 delta 语义的只有 `text_delta` 与 `thinking_delta`，没有任何 input/tool-input 增量事件 ⇒「逐 token 增量写入 + 行进度装饰」在这条线上依然不可达（事件总数与 sha 只住在 `corepack pnpm check:drift` 那一行的输出里，台账不抄第二份）。两条复测都是读文件，没有起旧产物。

- **侧栏全文搜索在这台内核上是死功能，不是"还没做完"**：`GET /sessions/search` 读 `rivetHome()/sessions/<slug>/<id>.jsonl`（CLI 扁平式），而 sidecar 把事件写在 `desktopDir()/sessions/<id>/events.jsonl`（桌面目录式）——两棵树不相交，所以**任何查询都 0 命中**（2026-10-11 实测：正文写进事件日志后仍查不到，见「上游缺陷」第一条）。客户端 UI、请求、渲染、判据都齐（`check:docs` 有一条两头对照的判定，内核对齐那天它会红），缺的只有内核那侧的路径一致。**这条不由我改**（非目标：不动 `src/**`），也不要把它读成"搜索待实现"。
- **暂态 401（已自愈，根因未定位）：直连 sidecar 曾对同一个 token 先 401 后 200**。复现事实（不是猜测）：`client/.sidecar-info.json` 里 `baseUrl=http://127.0.0.1:65076`、`pid 4420`、`token 8081dfb4…`；用它做 `authorization: Bearer <token>` 直连 `GET /sessions` → **401 Unauthorized**（`/health` 无鉴权所以 200），而同一时刻浏览器经 `serve-client` 的 `/api/sessions` → **200 拿到 39 个会话**。排除项都查过：`RIVET_SERVER_TOKEN` 环境变量**未设置**；全机只有这一份 `.sidecar-info.json`（`netstat` 显示 65076 只有 pid 17012 那个代理在连）；代理发的正是同一行 `authorization: Bearer ${sidecar.token}`（`scripts/serve-client.mjs:82`）；`Bearer`/裸 token/`x-tianshu-token`/带 `x-tianshu-protocol` 四种直连头部变体**全部 401**。**我原本那个「代理缓存的旧 token vs 文件里的新 token」解释已被证伪**：约 20 分钟后再用同一个文件、同一串 token 直连，得到的是 **200**；而 `client/.sidecar-info.json` 的 mtime 仍是 `2026-10-10T01:40:52`（从启动到现在没被改写过），token 头 8 位 `8081dfb4` 前后一致，`pid 4420` 一直活着，端口与 `/health` 的 `instanceId` 也没变。所以现象是**同一个 daemon 对同一串 token 的时间相关拒绝**，根因未知（`isAuthorizedRequest` 只做 sha256 + `timingSafeEqual`，看不到会随时间变化的分支，`src/server/auth.ts:18-23`）。**可执行的结论不变且更重要了**：直连前先打一枪 `GET /sessions`，401 就**先重试**（可能是暂态）再改走同源代理，别把 401 直接当成「sidecar 坏了」或「token 对不上」。**为什么值得记**：验收脚本若图省事直连 sidecar（复用默认 `clientRoot` info）就会撞同一条 401；`ci-smoke`/`stall-demo` 用自己独立的 state dir，历来正常。下次写直连脚本前先发一次 `GET /sessions` 探针，401 就改走同源代理，不要拿 401 当「sidecar 坏了」。

## 偏离计划之处（技术栈表里两格换了做法，记账）

计划 §7 写的是「pnpm monorepo + Vite + **tsdown**」和「React 18 + **CSS Modules**（禁组件库）」。实现里这两格换了做法，不是遗漏，是量过之后判定不划算：

- **tsdown 未用；包以源码被消费**。12 个包全部 `"exports": {".": "./src/index.ts(x)"}`，`apps/web/vite.config.ts` 把它们 alias 到自己的 src 入口，单测直接 `node --test` 跑 `.ts`（Node 24 的类型擦除），全仓零 per-package 构建产物。计划的 DoD 关心的是协议面与流式渲染，不是分包产物；加一层 tsdown 会带来 12 次构建、d.ts 生成与「改了源码但忘了先 build 就测到旧字节码」这一整类新失败，换来的只有发布 npm 包的能力——而这个客户端不发 npm。代价说清楚：**这些包目前不可独立发布**，若将来要（例如给第三方做界面），构建步要一次性补上。
- **CSS Modules 未用；改为「有界面的包各带一份 `styles.css`」+ `ui-theme/tokens.css` 里的自定义属性**。12 个包共 8 份界面样式，类名走 BEM 前缀（`.app__tabs`、`.wb__line`、`.set__prov-line`、`.tp-app`），作用域由「每包一个前缀」的约定而不是编译器保证。之所以换：主题切换要求所有颜色在运行时可变，`tokens.css` 里的自定义属性天然做到；而 CSS Modules 的哈希类名会让「暗色覆盖某组件的某个状态」变成跨文件猜哈希。这条选择的真实风险是**命名冲突**——目前 12 个包前缀互不相同，实测没有互相污染，但它靠约定，不靠工具。
- **§4.3 #4「组件经唯一 uSES 绑定订阅」与 #5「UI 组件按类订阅」：精神都守住了，字面两条都没照做**，这里如实记而不是含糊过去。实测计数（`grep` 全仓）：`useSyncExternalStore` 显式出现 **2 处**（`apps/web/src/App.tsx` 对 `SessionModel` 的一个、`packages/locale/src/index.ts` 的 `useT` 一个），另外 `apps/web` 用 zustand 的 `useStore(view, selector)` 读视图态 **8 处**（每个选择器内部也是一个 uSES 订阅）——所以**「唯一绑定」不成立，一共 10 个订阅点**。守住的其实是这条边界：**业务数据只有一个订阅点**（会话时间线全部经那一个 `SessionModel` 绑定进 React，store 里没有消息），视图态则天然是按字段选择器读的，8 个选择器读的是 `openSessionId`/`includeArchived`/`rightTab`/`panels.right`/`connection`/`generation`/`lastSeq`/草稿，都不是业务数据。**#5「按类订阅」没有实现成订阅粒度**：五类化（lifecycle/text/tool/state/custom）用在**折叠、计数与分组展示**上（`categorize` 喂状态条计数与 ContextPanel 分段），组件仍然从同一个会话快照取派生 props。为什么不按类拆订阅：一个 `tool` 块是 `tool_use` 与 `tool_result` 两个事件折叠出来的，按类切订阅就等于把一次折叠撕给两个订阅者各自维护，跨类的不变量（配对、open/seal）没人守得住；拆的代价换来的是「一类高频事件不会惊动所有面板」，而这一层现在靠**帧调度合帧**（`createFrameScheduler`，rAF 与超时赛跑）与渲染侧 `useMemo`（闭合块的 HTML 只解析一次，见上面的缩放测量）挡着。**如果将来出现证据说这不够**（例如某类事件让不相关面板明显掉帧），正确做法是给快照派生出版本号/切片再按需订阅，而不是把折叠撕开。
- 其余各格按计划：`zustand/vanilla + immer`、micromark 系块级增量解析、禁组件库、React 18、Vite 多入口构建，都在用。`shiki` 是唯一还没落的一格（见上条欠账）。
- **分包数：计划写「约 10 包」，实现是 12**。多出来的 `ui-files`（文件预览 + `@file` 候选）与 `ui-schedule`（定时任务看板）是把计划 M2 明列的两项各自成包，而不是塞进 `ui-chat`——`ui-files` 打 `/sessions/:id/files|list-dir|file-content`，`ui-schedule` 打 `/schedule*`，端点面完全不同，混在一起会让协议消费台账说不清归属。反过来，§4.1 图里提到的 `tool-card` **没有独立成包**：工具卡片和它的 diff/改前视图共享同一份 `Block` 折叠状态，拆开只会变成两个包互相传派生数据。两条都是包边界层面的取舍，不改变范围。
- **§4.4 桌面形态要求「preload 只暴露窗口控制/文件对话框（dsh 壳模式）」——实现里完全没有 preload**，这是刻意反着做的，理由与代价都说清：渲染进程是纯 Web 应用，只跟 127.0.0.1 说 HTTP，`nodeIntegration:false` + `contextIsolation:true` + `sandbox:true` 且**不放 preload**，等于「凡是壳可以不交出去的能力，一律不交」。preload 正是壳最容易失手放宽攻击面的地方，而工具结果与内嵌 MCP 视图都是模型可写的内容。代价实测为零：`grep` 过壳代码，**没有任何功能用到原生对话框或自定义窗口控制**（`dialog`/`showOpenDialog`/`setTitleBarStyle`/`frame:` 全无），窗口用的是系统边框。要什么才会被迫重新考虑：贴图附件（见下——其实内核有现成路由，不需要 preload）、自定义标题栏/无边框窗口、或需要 OS 级菜单快捷键时。
- **§7 风险表说 MVP「只消费 12 种最小集，其余容错忽略」——这条今天对上了，且有数**：`protocol-ledger` 从真实调用点算出 `ui-chat` 直接引用的 wire 事件字面量**恰好 12 个**（`context_budget`/`domain_usage`/`done`/`error`/`goal_state`/`hook_result`/`landing`/`phase`/`queue_pending`/`queue_status`/`status`/`user`），而 56 类全部经 `categorize` 落进五类、未知类型进 custom 不抛错——「最小集 + 容错」是实现了的，不是口号。
- **§2.3 借自 OpenCode 的「`/tui` 反向控制端点（server 驱动客户端 UI，P2 可选）」不可实施：内核根本没有这条路由**。`grep` 整个 `src/server/`，`tui` 字样只出现在 `clipboard-routes.ts:18` 的 `import { readImageFromClipboard } from '../tui/engine/clipboard-image.js'`（那是内核 TUI 的剪贴板模块，不是 HTTP 路由），路由表里也没有 tui/control/inject 类端点。所以这条不是「我们没做」，是**计划引用了一个本内核并不存在的能力**——写在这里免得下次又有人去找它。
