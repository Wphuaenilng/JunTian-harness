## 1. OpenCode（sst/opencode）—— HTTP+SSE 客户端/服务端分离的标杆

**与天枢 sidecar 最同构的项目，重点参考对象。**

### UI 形态与技术栈
- 启动 `opencode` 时同时拉起 **HTTP server（Bun + Hono 框架）** 和 **TUI 客户端**，TUI 只是 server 的一个客户端。
- TUI 技术栈经历过演进：早期是 Go + Bubble Tea，现版本为 **OpenTUI（Zig 渲染核心 + SolidJS 声明式 UI）**——性能敏感部分用 Zig，UI 逻辑用 SolidJS。
- 除 TUI 外还有：Web UI（React）、桌面端（Tauri）、IDE 插件（VS Code/Neovim）、TypeScript SDK（由 OpenAPI spec 用 Stainless 自动生成）。

来源：
- https://gist.github.com/shibuiwilliam/1d1466b24cb5c8f0d9367f2c75c9c064 （Dissecting OpenCode，逐源码拆解）
- https://cefboud.com/posts/coding-agents-internals-opencode-deepdive/
- https://nimbalyst.com/blog/what-is-opencode/

### 前后端通信协议
- **REST API 符合 OpenAPI 3.1 规范**，spec 暴露在 `/doc` 端点，可直接生成类型安全 SDK。
- **SSE 端点 `/global/event`**：所有客户端实时接收同一份流式事件，多客户端可同时连接同一 server 并同步看到输出。
- `opencode serve` 可无头运行；`opencode attach` 从远程/另一终端接入。
- 特殊设计：**`/tui` 端点反向驱动 TUI**——server 可以通过 API 向 TUI 预填/发送 prompt，IDE 插件借此控制 TUI。
- **per-project 隔离**：每个项目独立 SQLite（`~/.local/share/opencode/project/<hash>/data.db`），server 中间件按项目目录做请求作用域隔离，session 与权限不串项目。

来源：
- https://opencode.ai/docs/server/

### 流式渲染与工具调用展示
- 事件流走 SSE，事件只在**数据库事务提交后**才发射（Database.effect 设计），保证客户端看到的事件一定对应已持久化状态——重连后不会看到"幽灵事件"。
- 工具系统：Zod schema 定义 + 6 阶段 pipeline + 权限控制。

### 审批/权限交互
- 三态规则 `allow / ask / deny`，支持工具级、参数模式级（如 `bash: {"git *": "allow", "rm *": "deny"}`，**最后匹配的规则生效**）、per-agent 覆盖。
- 审批弹窗三个选项：**once / always / reject**；`always` 会按工具建议的安全前缀模式（如 `git status*`）加入会话级白名单。
- 默认 `read *.env` 被 deny；`doom_loop`（防死循环）和 `external_directory` 默认 ask。
- ⚠️ **已知坑**：headless 模式下若权限为 `ask`，server 端挂起等待永远不来的输入，agent 表现为"永久思考"（issue #16367）；桌面端曾有不读用户级权限配置的 bug（issue #36416）。

来源：
- https://opencode.ai/docs/permissions/
- https://github.com/anomalyco/opencode/issues/16367
- https://github.com/anomalyco/opencode/issues/36416

### 最值得借鉴的设计点
1. **OpenAPI-first + SSE 单事件总线**：协议即文档、文档即 SDK，任何能讲 HTTP 的东西都能成为客户端；这与天枢 sidecar 的 HTTP+SSE 完全同构，可直接对标。
2. **事件在事务提交后才发射**：流式事件与持久化状态强一致，天然支持多客户端同步与断线重连。
3. **`/tui` 反向控制端点**：server 不只是被动响应，还能驱动已连接的客户端（预填 prompt、执行命令），IDE 插件场景非常实用。

## 2. Aider —— 纯 CLI 极简主义 + git 即状态

### UI 形态与技术栈
- 纯 Python 终端 CLI（rich/prompt_toolkit 系），**没有真正意义上的前后端分离**。
- 有一个 **Streamlit 浏览器 UI**（`aider --browser` / `--gui`，`http://127.0.0.1:8501`），但社区定位是"远程桌面/结对围观"的辅助形态，非主力。

来源：
- https://computingforgeeks.com/aider-cheat-sheet/

### 流式渲染与 diff 交互
- 流式输出直接渲染在终端；`--show-diffs` 在提交前展示 diff（`context-window` 控制上下文行数）。
- **核心设计哲学：git 是跟踪 AI 改动的正确原语**——不用独立 diff 面板、不用 accept/reject 按钮：
  - 每次成功编辑**自动 git commit**（commit message 由弱模型生成）；
  - `/undo` 就是 `git reset`；`/diff` 看上一次改动；
  - 会话结束后 `git log` 就是一份可评审的 AI 工作记录。

来源：
- https://www.nxcode.io/resources/news/aider-complete-tutorial-guide-install-setup-2026
- https://www.deployhq.com/guides/aider

### 审批/权限交互
- 极简：没有细粒度工具权限矩阵，主要靠"是否自动提交"、"是否运行 lint/test"等开关；`--watch-files` 模式下甚至不交互——在任意编辑器里写 `AI!` 注释，aider 监听文件系统变化自动响应。

### 最值得借鉴的设计点
1. **用 git 替代自建审批/回滚体系**：对"AI 改了什么、怎么撤销"这个客户端最难的交互问题，aider 的答案是"不建，git 已经有"。Web/桌面客户端若把每次 turn 映射为可回滚的检查点（见 Cline 的 shadow git），比自研版本系统省力得多。
2. **`--watch-files` 的被动 sidecar 形态**：客户端不必是用户注意力的中心，可以监听外部事件（编辑器保存）异步工作——对桌面端"挂后台待命"形态有启发。

## 3. Cline / Roo Code（VS Code 插件）—— webview 架构与生成式流式 UI

### UI 形态与技术栈
- VS Code 侧边栏 **webview**：React SPA（Vite 构建）跑在 webview 沙箱里；扩展宿主（Extension Host）里是 TypeScript 的 Controller/Task 引擎。
- Cline 现已从早期 `postMessage` 字符串消息演进为 **gRPC-first**：所有 UI↔后端通信用 **Protocol Buffers over gRPC streaming**；proto 文件即接口定义（`proto/cline/state.proto` 等）。
- Roo Code 是 Cline 的 fork（同源架构），差异在产品层：多模式（Architect/Code/Ask/Debug/自定义 Mode，每个 Mode 有独立系统提示词、权限集和模型配置）。**注意：Roo Code 已于 2026-05-15 停止维护并归档**，但其 Mode 设计仍被社区 fork 继承。

来源：
- https://deepwiki.com/cline/cline/6.1-ui-architecture
- https://agent-safehouse.dev/docs/agent-investigations/cline
- https://github.com/unievo/xpilot/blob/main/AGENTS.md
- https://frontman.sh/blog/roo-code-vs-cline/

### 前后端状态同步
- **Command-Query 分离**：UI 只 dispatch 命令、订阅状态流。
- 状态水合 + 流式更新：webview 挂载时调 `StateServiceClient.getLatestState()` 拿全量快照，之后 `subscribeToState()` 订阅增量；扩展侧用 `getStateToPostToWebview()` 聚合状态后推送。
- 单例 Controller 集中编排；VS Code globalState/workspaceState/SecretStorage 分层持久化。

### 流式渲染与工具调用展示（本项目最精华的部分）
- **生成式流式 UI（generative streaming UI）**：工具执行结果（diff、浏览器操作、命令输出）实时可视化为富 UI 块，而非纯文本。
- **diff 流式落盘**：用 VS Code 原生 diff viewer + 自定义 virtual document provider 提供"改前"视图；模型每吐一段文本就**增量写入真实文件**，用户逐字符看到改动落盘。
- **竞态防护**：presentation lock 机制（渲染中加锁、置 pending 标志，渲染完补一轮），避免流式更新乱序。
- **流式进度装饰**：`activeLine` / `fadedOverlay` 两个 DecorationController——当前正在写入的行高亮、尚未生成的后续内容灰化，用户一眼看出"AI 写到哪了"。
- **Git shadow versioning（checkpoint）**：在影子 git 仓库里为每步操作建检查点，支持回滚且不污染用户 git 历史。

来源：
- https://memo.d.foundation/breakdown/cline

### 审批/权限交互
- Human-in-the-loop 是核心设计原则：文件编辑、终端命令默认逐项审批（Approve/Reject），可配置 auto-approve 白名单（按操作类型细粒度勾选）。
- Roo Code 的 **Mode 即权限集**：不同 Mode 自带不同的工具可用范围（如 Architect 不能写代码），把"角色"和"权限"绑定为一个用户可理解的概念。

### 最值得借鉴的设计点
1. **流式 diff 三件套**：virtual document（改前视图）+ 增量 WorkspaceEdit + activeLine/fadedOverlay 装饰——"看着 AI 写代码"的标杆实现，Web 端可用 Monaco diff editor + 同款装饰思路复刻。
2. **proto/schema 先行的消息契约 + Command-Query 分离**：webview 与宿主永不出现类型漂移，多 webview 实例（侧边栏+标签页）共享同一状态源。
3. **影子 git checkpoint**：审批通过一步、检查点落一个，回滚能力不依赖用户 git 纪律。

## 4. OpenHands（原 OpenDevin）—— 平台型 Web 前端

### UI 形态与技术栈
- **React SPA**（历史上 Remix，新一代 Agent Canvas 为 React + Vite + 路由表），TypeScript，Tailwind。
- 状态管理是**混合架构**：Redux 管 UI 态与实时事件，React Query 管服务端数据缓存，Zustand（新版 event store）管去重后的事件流，Context 管 WebSocket 连接等横切关注点。
- 后端 FastAPI（Python），Docker 沙箱 per conversation。

来源：
- https://deepwiki.com/All-Hands-AI/OpenHands/9-frontend-application
- https://pyshine.com/OpenHands-Agent-Canvas-Source-Tour/

### 前后端通信协议
- **REST + WebSocket（Socket.IO）双通道**：REST 管会话 CRUD/设置/历史，WebSocket 管实时 agent 事件。
- 值得注意的演进：会话初始化**从 WebSocket INIT 事件迁移到 REST `POST /api/conversation`**——用 REST 做可靠的状态变更，WebSocket 只做事件流，职责更干净。
- **可恢复事件流**：重连用 **last event ID 续传**，REST 拉历史 + WS 接增量，两端在 Zustand store 里**去重合并**——刷新页面不丢上下文。
- 限流处理消息防止 UI 阻塞；WS 事件触发 React Query 缓存失效（如文件操作后自动刷新 git changes 视图）。
- ingress 代理把前端、agent server、automation 服务统一在同一 origin 下按路径路由，本地一条命令拉起全栈。

来源：
- https://arxiv.org/html/2609.37216v1 （附录中引用的 PR：session 初始化从 WS 迁 REST）
- https://deepwiki.com/All-Hands-AI/OpenHands/9-deployment-and-integration

### 审批/权限交互
- 确认模式（confirmation mode）+ 安全风险分析器（security analyzer 对动作打风险分级）；浏览器/终端/VS Code Web 都内嵌为前端面板，agent 动作以带语法高亮的事件卡片流呈现。

### 最值得借鉴的设计点
1. **"REST 改状态、WS 推事件"的通道分工** + last-event-id 断线续传 + 事件去重合并 store——SSE/WS 客户端重连的正确姿势，天枢 Web 客户端可直接照搬。
2. **WS 事件驱动查询缓存失效**：实时事件不只是渲染，还反向触发相关数据的重新拉取，保证面板数据（文件变更、git 状态）永远新鲜。

## 5. Gemini CLI（google-gemini/gemini-cli，Apache-2.0）

### UI 形态与技术栈
- **Ink（React 渲染到终端，用的是 `@jrichman/ink` fork）**，整个交互 UI 是 React 组件：约 **270 个 .tsx**（布局、消息渲染、对话框、DiffRenderer、MarkdownDisplay、Composer 等）。
- TypeScript monorepo（npm workspaces）：`packages/cli`（UI/输入/历史/主题）与 `packages/core`（API 客户端、prompt 构建、工具注册执行、会话状态）**进程内分包**——不是网络 C/S，而是模块边界。
- **核心包不提供 Web UI**；对外集成走三条旁路：DevTools（WebSocket 25417）、VS Code companion（Express 本地 HTTP）、A2A server（Express）。

来源：
- https://agent-safehouse.dev/docs/agent-investigations/gemini-cli
- https://google-gemini.github.io/gemini-cli/docs/architecture.html

### 流式渲染与工具调用展示
- 工程规范值得抄：**状态迁移集中化、快捷键注册唯一化（keyBindings.ts 数据驱动）、文本测量布局化（MaxSizedBox + ResizeObserver）、快照测试双层（文本 + SVG）**。
- DiffRenderer / CodeColorizer / MarkdownDisplay 分离；支持 vim 模式、自定义主题、屏幕阅读器（accessibility）布局。

来源：
- https://blog.gitcode.com/93d74304ea74e532e771237d6fadc233.html

### 审批/权限交互
- 工具按"是否修改文件系统/执行 shell"分级：写操作先展示工具与参数详情、需用户批准；只读操作可免确认。
- checkpointing：文件修改前保存 git 快照 + 对话历史，`/restore`、`/rewind` 回滚。

### IDE/外部集成
- **`gemini --acp`：Agent Client Protocol 模式**，不渲染 TUI，作为常驻进程在 stdio 上讲 JSON-RPC 2.0，由编辑器代理创建会话、发 prompt、切审批模式、代理文件系统访问。Gemini CLI 是 ACP 的首个参考实现。

来源：
- https://blog.gitcode.com/eb40ba9d37ebccc4541161a9bee2e756.html

### 最值得借鉴的设计点
1. **React/Ink 组件化 TUI 的工程化规范**：数据驱动快捷键、SVG 快照测试等——如果天枢 TUI 继续演进，这套规范直接可用。
2. **审批按"副作用"分级**：只读免确认、写操作必确认，规则简单用户可预期。

## 6. Codex CLI（openai/codex）—— 一个内核、五种前端

### UI 形态与技术栈
- 2025-05 从 TypeScript+Ink **全量重写为 Rust**：零依赖单二进制、原生沙箱绑定（Seatbelt/Landlock/Windows 受限 token）、无 GC 停顿。
- TUI 用 **Ratatui**（immediate-mode 渲染，每帧全量重绘，无 retained state 过期问题）+ crossterm；UI 变更强制 `insta` 快照测试。
- `codex-rs/` Cargo workspace 80+ crate 分层：core（agent 大脑）/ protocol（共享协议类型）/ tui / exec / app-server / sandboxing…

来源：
- https://aiidelist.com/codex-architecture
- https://codex.danielvaughan.com/2026/03/28/codex-rs-rust-rewrite-architecture/
- https://zread.ai/openai/codex/10-agent-system-and-multi-agent-orchestration

### 前后端通信协议（本项目最精华的部分）
- **SQ/EQ（Submission Queue / Event Queue）双队列模式**：UI 提交 `Op`，核心异步回 `Event`，协议类型定义在独立的 `codex-protocol` crate——UI 与引擎的"共享语言"。
- **接入层五种前端全是可插拔薄壳，全部走同一协议**：
  1. TUI（ratatui）——注意 **TUI 不直接调 core**，而是内嵌一个 in-process app-server，用标准 RPC 请求完成所有会话操作；
  2. exec（无头，JSONL 事件流，脚本/CI/SDK 底层）——同样经 `InProcessAppServerClient` 而非直连 ThreadManager；
  3. app-server（JSON-RPC 2.0，VS Code/桌面/手机端的统一入口，同一组进程服务所有富客户端）；
  4. MCP server（把自己暴露为工具给其他 agent）；
  5. TS/Python SDK（底层 spawn `codex exec`）。
- **`ts-rs` 从 Rust 类型直接生成 TypeScript 类型**，Rust 与 TS 客户端 wire format 永不漂移。

来源：
- https://www.iceyao.com.cn/post/2026-08-23-codex-cli%E6%BA%90%E7%A0%81%E6%B7%B1%E5%BA%A6%E6%8A%80%E6%9C%AF%E8%A7%A3%E6%9E%90/
- https://api.treerouter.ai/en/blog/codex-cli-agent-runtime-architecture
- https://ai-insight.org/reports/codex-mobile-deep-dive-2026

### 流式渲染与工具调用展示
- 流式渲染模型推理内容与工具执行 diff；token 消耗实时统计；审批弹窗是 TUI 内 popup。
- 配色约定：cyan=提示、green=成功、red=错误、magenta=品牌。

### 审批/权限交互
- 审批模型是协议层一等公民（approval 类型定义在 `codex-protocol`）；支持 PermissionRequest hook（stdin JSON 输入、stdout 返回 allow/deny 决定，可被外部程序自动审批）；沙箱策略与审批解耦——deny 规则优先于任何 hook。

来源：
- https://openrouter.ai/docs/cookbook/coding-agents/auto-approve-permission-prompts-with-jev

### 最值得借鉴的设计点
1. **"连自己人都走协议"的纪律**：TUI/exec 也经 in-process app-server 通信，而不是绕过协议直连内核——这保证任何第三方客户端拿到的能力与官方 TUI **完全一致**，没有"内部 API 比公开 API 强"的双轨问题。这是 sidecar 架构最容易偷工减料、也最值得坚持的一条。
2. **协议类型独立成包 + 代码生成多语言客户端类型**（ts-rs → TS）：对应天枢可用 OpenAPI/JSON Schema → TS 类型生成达到同样效果。
3. **SQ/EQ 双队列**：命令与事件分离的异步模型，天然适配 SSE 推事件 + HTTP 收指令的 sidecar 协议形态。

## 7. Goose（block/goose → AAIF）—— 双客户端整合失败的反面教材与自救

### UI 形态与技术栈
- 三个 Rust 二进制包同一个核心 `Agent`：
  - `goose`（CLI）：**进程内直调**，无协议；
  - `goosed`（server）：bespoke **REST + SSE HTTP API，103 个端点**；
  - `goose-acp-server`：ACP 协议封装（Zed/JetBrains 集成）。
- 桌面端：**Electron + React 19 + Vite + Tailwind**（Electron Forge 打包），spawn `goosed` 子进程，经 HTTP/WebSocket 通信。另有 `goose web`（axum server，端口 3000，自动开浏览器）。

来源：
- https://github.com/aaif-goose/goose/discussions/7697 （Goose Client/Server 官方讨论）
- https://agent-safehouse.dev/docs/agent-investigations/goose
- https://deepwiki.com/block/goose/1-overview

### 关键教训：他们正在拆掉自己的架构
官方博客自述：CLI 进程内直调 + 桌面走 goosed REST/SSE，**两条集成路径导致每个新功能（session 管理、扩展加载、流式）都要接两遍**，第三方开发者没有标准接入方式。解决方案：

- **统一到 ACP 一个协议**：交互模式 = CLI 作为 ACP 客户端对讲进程内 agent；`goose serve` = 同一 ACP 接口走 HTTP/WebSocket 暴露给桌面/移动/bot。
- **一个二进制、一个协议**；桌面端从 Electron 重写为 **Tauri**（基于 ACP 客户端）；计划最终删除 goosed 和旧 Rust CLI。

来源：
- https://goose-docs.ai/blog/2026/04/08/goose-acp-and-new-tui/ （goose 2.0 beta 官方架构博客）

### 审批/权限交互
- agent runtime 内置 permission 层；凭证走系统 keyring（macOS Security.framework / Linux secret-service / Windows Credential Manager），回退明文 YAML。

### 最值得借鉴的设计点（含教训）
1. **反面教材：不要让任何一个客户端绕过协议**。Goose 的"CLI 直调、桌面走 server"双轨是 2026 年 agent 客户端架构最著名的技术债案例——天枢 TUI 应与 Web/桌面端一样，都是 sidecar 协议的普通客户端。
2. **正面参考：向 ACP 收敛**。编辑器↔agent 集成正在被 ACP 标准化（见第 9 节），自研协议应至少在语义层与 ACP 的概念（session/prompt/工具调用报告/权限请求/diff）对齐，未来可低成本出 ACP 适配层。

## 8. Crush（charmbracelet/crush）—— Bubble Tea TUI 的美学上限

### UI 形态与技术栈
- 纯 Go 单二进制 TUI，单进程无分离。**Charm 全家桶**：Bubble Tea v2（TUI 框架）+ Lip Gloss v2（样式）+ Glamour v2（终端 Markdown 渲染）+ Fang（CLI）。
- 分层：TUI → Coordinator（管理 coder/task 等命名 agent）→ Fantasy（LLM provider 抽象层）→ 工具/MCP/LSP；SQLite + sqlc 做会话持久化。

来源：
- https://pyshine.com/Crush-Glamourous-Agentic-Coding-For-All/
- https://github.com/charmbracelet/crush

### 流式渲染与工具调用展示
- diff 提案以 unified diff 渲染在 TUI 内，**inline apply/reject**；多文件重构渲染为文件级 diff 树，支持全收或逐文件接收。
- 每次 MCP 工具调用记录日志，可导出 JSON 审计；会话转录存 `~/.crush/sessions/` JSON 可回放。

来源：
- https://x-cmd.com/install/crush/

### 审批/权限交互
- **per-tool 权限 allow / deny / ask**；默认交互模式逐步确认编辑与 shell；`--yolo` 全自动（定位是容器/CI 内使用）。
- `.crushignore`（gitignore 语法）把秘密/产物目录挡在 agent 视野外——**视野级权限**而不仅是动作级权限。

### 最值得借鉴的设计点
1. **Markdown/diff 渲染质量即产品力**：Crush 证明 TUI/Web 端"好看"本身是差异化竞争力（Glamour 渲染管线可对标 Web 端 Markdown 渲染器的选型）。
2. **diff 树 + 逐文件 apply/reject**：多文件改动的审查交互，比逐字符流式 diff 更适合"审查模式"。
3. **`.crushignore` 视野隔离**：权限设计除了"能不能执行"，还有"能不能看见"——`.env` 类敏感文件应在上下文收集层就被排除。

## 9. 其他有特色的项目与行业级趋势

### 9.1 ACP（Agent Client Protocol）—— 编辑器↔agent 的"LSP 时刻"
- Zed 2025-08 发布（Apache-2.0），**JSON-RPC 2.0 over stdio**，编辑器以子进程方式拉起 agent；远程 agent 的 HTTP/WS transport 在演进中。
- 标准化了**编辑器需要的 UX 词汇**：session 生命周期、prompt、流式响应、**编辑器可渲染与审批的 file diff、权限请求（permission request）**；尽量复用 MCP 的 JSON 表示。
- 采用面（2026 年中快照）：25~40+ agent（Claude Code、Codex CLI、Gemini CLI 原生、OpenCode、Goose、Cline、Kimi CLI、Qwen Code、Copilot CLI…）；客户端有 Zed、JetBrains 全系（原生）、Neovim/Emacs 插件、Devin Desktop、marimo 等；Zed+JetBrains 2026-01 共建 **ACP Registry**。
- **UX 归属原则：编辑器拥有 UX**（文件树、终端、diff、prompt 框），agent 只提供能力。
- 注意 `session/load` 的语义：历史归 agent 所有，加载=agent 把对话**以通知流重放**给客户端重绘——客户端不持有状态。

来源：
- https://contracollective.com/blog/agent-client-protocol-acp-devin-desktop-editor-agent-standard-2026
- https://mcp.directory/blog/agent-client-protocol-vs-mcp-2026
- https://tomrochette.com/agents/acp/
- https://menuagentic.com/blogs/agent-session-handoff-drops-the-transcript/

### 9.2 Plandex —— 客户端/服务端 + 累计 diff 沙箱
- Go 写的 CLI/REPL（fuzzy 自动补全）+ 自托管 Server（REST 60+ 端点，管账号/项目/plan/分支/上下文/diff/流式执行；PostgreSQL + LiteLLM proxy）。
- **Cumulative diff review sandbox**：AI 的改动先落在隔离的草案缓冲区，不碰工作区；跨 20+ 文件的大型 plan 可以**整体审查、按文件拒绝、只应用批准的部分**；支持 branch/rewind/diff 任意 plan 状态。
- 与 Aider（边生成边落盘）和 Claude Code（落盘后靠 git 回滚）形成第三种范式。
- ⚠️ 项目现状：2025-10 云服务关停、公司停止运营，repo 进入维护模式——但其 diff 沙箱设计被公认仍有独有价值。

来源：
- https://github.com/api-evangelist/plandex
- https://aicoderscope.com/blog/plandex-v2-review-2026/
- https://cursor-alternatives.com/blog/plandex-faq/

### 9.3 Void —— fork 编辑器的警示
- Void fork 了整个 VS Code 做 AI 编辑器（Electron，自改 workbench、EditCodeService 流式写 buffer、自定义 IPC）。**教训：fork 编辑器获得 UI 控制力，但陷入对上游的永久维护赛跑**；模块化扩展路线（Cline）规避了这一点。对"要不要自己 fork 一个 IDE 壳"的问题，答案是明确的否定——自研桌面客户端用 Tauri/Electron 嵌编辑器组件（Monaco）即可。

来源：
- https://fast.io/resources/cline-vs-void/

### 9.4 权限自动化的前沿：hook 化审批
- 社区出现以 **PermissionRequest hook** 外挂自动审批程序的实践（如 Jev/Jevvy，对 OpenCode/Claude Code/Codex/Cursor 四家做风险打分自动放行）；各家共同约束：**deny 规则优先于任何 hook**，hook 只能放宽 ask 不能推翻 deny。

来源：
- https://openrouter.ai/docs/cookbook/coding-agents/auto-approve-permission-prompts-with-jev

## 10. 对天枢自研 Web/桌面客户端的启示

### A. 已被验证为行业共识（应该做）

1. **UI 与 agent 内核尽早分离，且"自己人也不许绕过协议"**。
   OpenCode 的 TUI 是 HTTP 客户端；Codex 的 TUI/exec 都走 in-process app-server；Goose 用血的教训证明双轨集成（CLI 直调+桌面走 server）必然还债。天枢 TUI 必须消费与 Web/桌面端**完全相同**的 sidecar HTTP+SSE 协议，不给内核留"内部直调后门"。（来源见 §1/§6/§7）

2. **"命令走请求/响应，事件走推流"的双通道分工**。
   OpenCode：REST + SSE `/global/event`；OpenHands：REST 改状态 + WS 推事件（且特意把会话初始化从 WS 迁到 REST）；Codex：SQ/EQ 双队列。结论一致：**状态变更用可靠的请求/响应，实时输出用单向推流**。天枢 HTTP+SSE 协议形态与行业主流完全对齐，坚持即可。（来源见 §1/§4/§6）

3. **协议 schema 先行，客户端类型代码生成**。
   OpenCode 用 OpenAPI 3.1 `/doc` + Stainless 生成 SDK；Cline 用 protobuf；Codex 用 ts-rs 生成 TS 类型。天枢应给 sidecar API 出 OpenAPI 文档，TS 客户端类型一律生成而非手写——消灭 wire format 漂移。（来源见 §1/§3/§6）

4. **断线重连 = 事件 ID 续传 + 历史/增量去重合并**。
   OpenHands 的 last-event-id + REST 历史 + WS 增量在 store 内去重合并是成熟范式；OpenCode 的"事件在事务提交后发射"进一步保证事件与持久态一致。SSE 客户端必须带 `Last-Event-ID` 重连语义，且 UI 状态能由"快照+事件流"重建（刷新页面不丢会话）。（来源见 §1/§4）

5. **审批三态 + 分级默认值 + once/always/reject**。
   OpenCode 的 allow/ask/deny + 模式匹配（最后匹配生效）+ 工具建议安全前缀白名单；Gemini CLI 的"只读免确认、写操作必确认"；Codex 的审批作为协议层一等类型。共同结论：权限模型要做进协议（不是 UI 层的事后拦截），deny 优先级最高、不可被任何 hook/自动审批推翻；`.env` 类敏感文件默认拒绝（视野级隔离，对标 Crush 的 `.crushignore`）。（来源见 §1/§5/§6/§8）

6. **可回滚检查点是标配**。
   Aider 的 git 自动提交、Cline 的影子 git checkpoint、Gemini CLI 的 `/restore`/`/rewind`、Plandex 的 plan 版本——"AI 每步操作可撤销"已是及格线。推荐 Cline 式影子 git：不污染用户历史、无需用户有 git 纪律。（来源见 §2/§3/§5/§9.2）

7. **headless 模式必须有审批的出路**。
   OpenCode 的 issue #16367（serve 模式下 `ask` 权限导致永久挂起）是反面教材：无头运行时，`ask` 必须能被路由到某个已连接客户端回答，或显式降级为 allow/deny 并在启动时告警。（来源见 §1）

### B. 差异化亮点（可以做）

1. **server 反向驱动客户端的端点**（OpenCode `/tui`）：外部工具（IDE 插件、bot、定时任务）可通过 sidecar 向正在运行的客户端预填/发送指令——天枢已有 sidecar 协议，加一个"控制已连接客户端"的端点成本很低、生态价值高。（§1）
2. **流式 diff 三件套**（Cline）：virtual document 改前视图 + 增量写入 + activeLine/fadedOverlay 进度装饰。Web 端用 Monaco diff editor 复刻，"看 AI 逐行写代码"是最强的心智占领交互。（§3）
3. **双模式审查交互**：生成中=流式 diff（Cline 式）；生成后=diff 树按文件 apply/reject（Crush 式）；大宗改动=草案沙箱整体审查（Plandex 式）。三种粒度对应三种任务规模，可分层实现。（§3/§8/§9.2）
4. **Mode 即权限集**（Roo Code 遗产）：把"角色（plan/build/review）"和"该角色的工具权限+模型配置"打包成用户可切换的 Mode，比裸权限矩阵易懂得多。Roo 已归档，这个设计正值无主可捡。（§3）
5. **被动 sidecar 形态**（Aider `--watch-files`）：桌面端挂后台监听编辑器保存/剪贴板事件异步响应，客户端不必是对话框。（§2）
6. **WS/SSE 事件驱动缓存失效**（OpenHands）：事件流不只驱动消息列表，还触发文件变更、git 状态等面板的自动刷新。（§4）
7. **Tauri 优先于 Electron**：OpenCode 桌面端选 Tauri，Goose 正从 Electron 迁往 Tauri——Rust 生态 + 更小的包体是 2026 年桌面 agent 客户端的明显风向；若团队是 TS 全栈，Electron 仍是稳妥选项。（§1/§7）
8. **对齐 ACP 语义**：即使不上 ACP，sidecar 协议的概念模型（session/prompt/工具调用/permission request/file diff）应与 ACP 对齐，保留未来接入 Zed/JetBrains 生态的适配空间。（§9.1）

### C. 被反复踩过的坑（避免做）

1. **双轨集成**（Goose）：任何一个客户端绕过协议直调内核，每个新功能就要做两遍，最终被迫重写。代价：Goose 正在删 goosed + 旧 CLI + 重写桌面端。（§7）
2. **headless 挂死**（OpenCode #16367）：审批请求没有投递路径时静默挂起、无任何错误提示——用户视角是"agent 死了"。（§1）
3. **fork 编辑器**（Void）：为 UI 控制力 fork VS Code = 永久追上游的维护赛跑，项目已死。桌面端嵌 Monaco/现成组件即可。（§9.3）
4. **WebSocket 大包大揽**（OpenHands 修正过的路线）：把可靠状态变更（如创建会话）塞进 WS 消息里做，后来被迫迁回 REST。WS/SSE 只承载"可丢失可续传"的事件。（§4）
5. **retained-state UI 过期**（Codex 选 Ratatui 的理由之一）：长会话下保留式 UI 状态容易与内核漂移；对策是事件溯源式 UI——状态可由快照+事件流重建，而非组件各自囤积状态。OpenHands 的事件去重 store、Cline 的单一 ExtensionStateContext 都是同一思想。（§3/§4/§6）
6. **权限配置多端不一致**（OpenCode #36416：桌面端不读用户级权限）：权限规则必须在 server 侧统一求值，客户端只负责呈现审批 UI——绝不能每个客户端自己解释配置文件。（§1）
7. **没有类型生成的手写协议客户端**（Cline/Codex/OpenCode 三家的共同选择即反证）：手写消息类型必漂移。（§1/§3/§6）

### D. 一页纸结论

> 天枢的 sidecar（HTTP+SSE）路线与 2026 年行业主流（OpenCode、OpenHands、Codex app-server）**方向完全一致**，这是最大的定心丸。
> 落地优先级建议：
> **P0**（共识）：协议 schema/OpenAPI 先行 + TS 类型生成；REST 命令 + SSE 事件双通道；事件带 ID 可续传；权限模型进协议（三态 + deny 最高优先）；影子 git 检查点；TUI 也走协议。
> **P1**（差异化）：Cline 式流式 diff + 进度装饰；审批 once/always/reject + 安全前缀白名单；headless 审批路由。
> **P2**（生态）：server 反向控制端点；Mode=权限集；ACP 语义对齐/适配层；Tauri 桌面壳。
